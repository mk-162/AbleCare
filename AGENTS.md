# TinaCMS Cloud indexing

`tina/tina-lock.json` is **committed** and is the schema Tina Cloud reads to
index this repo (the cloud does **not** run `tinacms build`). If you change
`tina/config.ts`, you MUST regenerate the lock (`npm run tina:lock`) and commit
it, or Tina Cloud branch indexing breaks ("indexing branch failed" /
"Unable to seed …") even though `tinacms audit` passes. CI enforces this
(`.github/workflows/tina-lock-check.yml`). Note `tina/__generated__/` is the
opposite: gitignored, regenerated by the host build — never commit it.

Full diagnosis + fix + prevention runbook (portable to other Tina projects):
**[`docs/tina-cloud-reindex-runbook.md`](docs/tina-cloud-reindex-runbook.md)**.

The same applies when **upgrading** `tinacms` or `@tinacms/cli`: a new CLI
stamps a new schema version into the lock, so run `npm run tina:lock` and commit
it alongside the bump. Dependabot cannot do this, so its Tina PRs fail
`tina-lock-check` until someone does (they are grouped separately in
`.github/dependabot.yml` for that reason).

# Tina media: new images must reach `main` first

Tina rewrites every `image` field to its media CDN
(`https://assets.tina.io/<clientId>/<path>`, see `media.tina` in
`tina/config.ts`). The CDN holds **one** copy per project and syncs it from
`main`. So an image committed only to a branch renders as an empty `src` on
that branch's preview, even though the file is in `public/`.

When staging content with a new image on `dev` or a feature branch, put the
image file on `main` first (unreferenced is fine), then reference it from the
branch. Pages that read the filesystem directly rather than through Tina, such
as `data/case-studies/*.json`, use plain `/images/...` paths and are not
affected.
